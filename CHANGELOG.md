## [0.1.53]
- **A fresh install has a version to compare.** The client zip and the Prism zip already carried `.autis/version.txt` (`0.1.52\n` in 0.1.52). The CurseForge zip did not, so a fresh import had nothing for `autis_updater_setup` to compare. The release workflow now writes `overrides/.autis/version.txt` into the CurseForge zip. The bytes are the release version plus a newline, the same text the updater writes after it applies a pack. The client zip stays `.autis/version.txt` and the Prism zip stays `.minecraft/.autis/version.txt`. The server pack does not get the file. If `.autis/version.txt` is missing or blank, the updater logs `no .autis/version.txt — skipping the update` and records `skipped-no-version`, and the setup mod logs `curseforge mode: no .autis/version.txt, skipping the update check`. Neither one downloads, and neither one writes a version file, so the next launch does the same thing instead of updating again. `java -jar autis/updater.jar --force` still updates.
- **CurseForge runs the updater after the game closes.** `autis_updater_setup` 1.0.2 replaces 1.0.1 and stays in `.pakku/client-overrides/mods/`. On a Windows CurseForge test of 1.0.1, the launcher held its instance in memory and wrote it back: the master `MinecraftGameInstance.json` was reset to `javaArgsOverride: null` one second after the post-exit rewrite, and `minecraftinstance.json` was overwritten at the next launch. No `autis/updater.log` was produced. The "curseforge master already hooked" line was also wrong when the master had two entries named Autisnautics-1.21 and neither had the hook. 1.0.2 does not write `minecraftinstance.json` or `MinecraftGameInstance.json` to add `-javaagent:autis/updater.jar`. If that token is already a whole JVM argument in a JSON string, a post-exit pass removes just that token; any other shape is left unchanged. At startup the mod reads `.autis/version.txt` and follows `https://github.com/InvalidArgument3/Autisnautics-1.21/releases/latest` the same way `autis/updater.jar` does. When the release is newer, it detaches a helper that waits until the game pid is gone, then runs `javaw -jar autis/updater.jar --game-dir <instance>` so the updater's own dialog can apply the pack. On Windows the java path is the executable that launched the game (`ProcessHandle` command), with `java.exe` swapped for the sibling `javaw.exe` when that file exists, otherwise `java.home\bin\javaw.exe`. The path is captured before exit and passed into the helper. A toast says the update will be installed when the game closes. Prism and MultiMC keep the 1.0.1 `PreLaunchCommand` hook and the post-exit rewrite. The log is still `autis/updater-setup.log`, with one line in `latest.log`.

## [0.1.52]
- **The Prism hook survives Prism's exit save.** On a fresh 0.1.51 CurseForge import, `autis_updater_setup` 1.0.0 wrote `PreLaunchCommand` at launch and again from the shutdown hook, then Prism saved `instance.cfg` from memory about 10 ms after the game exited and wiped `PreLaunchCommand` and `OverrideCommands`. The post-exit helper never started. The log said `no jar path`, because NeoForge's jar filesystem hides the mod's CodeSource. 1.0.1 (replaces 1.0.0, still `.pakku/client-overrides/mods/`) copies the mod to `autis/updater-setup-helper.jar` and starts that file with the Java that launched the game. On Linux and macOS the helper is `setsid` plus `nohup`, including inside Flatpak Prism, where the instance lives under `~/.var/app/org.prismlauncher.PrismLauncher/`. On Windows it is `start /b`. It waits until the game PID is gone and the watched launcher file has been quiet for a second, up to 30 seconds, then patches and logs whether the hook is still in the file. The next launch logs `previous write stuck` or `previous write was overwritten` while `autis/updater-setup.state` is `pending`. `latest.log` gets one INFO line, `[autis_updater_setup] patched prism`, `[autis_updater_setup] prism already hooked`, or `[autis_updater_setup] unsupported launcher`. A real Flatpak Prism import confirmed `post-exit rewrite verified`, and the next launch ran the updater and showed the update dialog. The jar stays in `.pakku/client-overrides/mods/`, so the server pack does not get it.

## [0.1.49]

## [0.1.44]
- **The updater updates itself.** The pack already ships `autis/updater.jar` inside the client zip; it was ignored because `autis/` is protected from being written. Now the staged jar is compared with the installed one and, when it differs, parked as `autis/updater.pending.jar` and swapped in by a detached helper two seconds after the updater exits, because Windows cannot replace a jar the JVM still holds open. A swap that does not complete is retried at the next launch before anything else runs, and the file is only ever replaced when the bytes differ, so a pack that ships an unchanged jar does nothing.
- **Two paths, both tested.** Linux replaces immediately (the running jar can be unlinked); Windows queues the pending copy and the helper does `move /y` after the process is gone. A leftover pending file left by an interrupted update is consumed on the next start rather than accumulating.

## [0.1.41]
- **The pack updates itself on launch.** `autis-updater.jar` sits in `minecraft/autis/`, and the launcher runs it as a pre-launch command. It reads the newest release tag from GitHub, compares it with `.autis/version.txt`, and when the release is newer downloads `Autisnautics-1.21-latest-client.zip` and applies it over the instance.
